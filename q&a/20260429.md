# Distributed Training Q&A

## 1. What is a communication group? What is a rank?

A **communication group** (or **process group**) is a set of distributed worker processes that can communicate with each other using distributed primitives such as `broadcast`, `all_reduce`, `all_gather`, and `barrier`.

In PyTorch distributed training, each process usually controls one GPU. The default group is often called the **world group** and contains all distributed processes. We can also create smaller groups, for example:

- one data-parallel group,
- one tensor/model-parallel group,
- one pipeline-parallel group,
- one subgroup per node.

A **rank** is the integer ID of a process inside some group.

| Term | Meaning |
|---|---|
| **Global rank / world rank** | The process ID in the full world group, usually from `0` to `world_size - 1`. |
| **Local rank / rank in node** | The process ID within one physical machine. This is usually used to choose the local GPU, e.g. `cuda:LOCAL_RANK`. |
| **Group rank / rank in communication group** | The process ID within a specific process group. This can differ from the global rank because the group may contain only a subset of all workers. |

Example: suppose there are 2 nodes, each with 4 GPUs, so `world_size = 8`.

| Global rank | Node | Local rank |
|---|---:|---:|
| 0 | 0 | 0 |
| 1 | 0 | 1 |
| 2 | 0 | 2 |
| 3 | 0 | 3 |
| 4 | 1 | 0 |
| 5 | 1 | 1 |
| 6 | 1 | 2 |
| 7 | 1 | 3 |

If we create a communication group containing global ranks `[0, 2, 4, 6]`, then those same processes have group ranks `[0, 1, 2, 3]` inside that group.

## 2. List the communication primitives we have learned so far, and explain each one

The main primitives are:

| Primitive | Function |
|---|---|
| **`send` / `recv`** | Point-to-point communication. One rank sends a tensor to another rank, and the destination rank receives it. Useful for custom communication patterns or pipeline parallelism. |
| **`isend` / `irecv`** | Asynchronous point-to-point communication. Starts the send/receive operation and returns a handle, so computation can overlap with communication. |
| **`barrier`** | Synchronization primitive. All ranks in the group wait until every rank reaches the barrier. Useful before cleanup, timing, or phase changes. |
| **`broadcast`** | One source rank sends the same tensor to all other ranks. In DDP this is often used to copy rank 0's initial model parameters to every other rank. |
| **`reduce`** | All ranks contribute tensors, an operation such as sum/max/min is applied, and only one destination rank receives the result. |
| **`all_reduce`** | All ranks contribute tensors, the reduction is applied, and every rank receives the final result. DDP uses this to average or sum gradients across data-parallel workers. |
| **`scatter`** | One source rank splits a tensor/list of tensors and sends one chunk to each rank. |
| **`gather`** | The inverse of scatter. Each rank sends a tensor to one destination rank, and the destination rank receives the full list. |
| **`all_gather`** | Every rank contributes a tensor, and every rank receives the list/concatenation of all tensors. Useful for collecting shards, logits, activations, or validation results from all ranks. |
| **`reduce_scatter`** | Combines reduce and scatter. First, corresponding elements/chunks are reduced across ranks; then each rank receives only its reduced shard. This is common in sharded data parallelism and optimizer-state sharding. |
| **`all_to_all`** | Every rank sends a different chunk to every other rank and receives a different chunk from every other rank. Useful for expert parallelism, sequence parallelism, and data reshuffling. |

Two useful equivalences:

- `all_reduce` is approximately `reduce` followed by `broadcast`.
- `reduce_scatter` is approximately `all_reduce` followed by keeping only one shard.

In practice, libraries implement these directly because the optimized algorithms are faster than manually composing simpler primitives.

## 3. Why might we want to use parallelism strategies for scaling?

We use parallelism because a single GPU or machine eventually becomes a bottleneck in **memory**, **compute**, or **time**.

Main reasons:

1. **Fit larger models.** A model's parameters, gradients, optimizer states, and activations may not fit on one GPU.
2. **Train faster.** More GPUs can process more tokens/examples per second.
3. **Use larger effective batches.** Data parallelism lets each worker process a local mini-batch, then synchronize gradients to behave like one larger global batch.
4. **Reduce per-device memory pressure.** Model, optimizer, gradient, and activation sharding spread state across devices.
5. **Scale beyond one machine.** Large LLM training usually requires many GPUs across many nodes.

Common strategies:

| Strategy | What is split? | Main benefit |
|---|---|---|
| **Data parallelism** | Training data | Increases throughput when the full model fits on each GPU. |
| **Tensor/model parallelism** | Individual layers or tensors | Allows layers too large for one GPU. |
| **Pipeline parallelism** | Different layers/stages | Splits a deep model across GPUs. |
| **Sharded data parallelism / ZeRO / FSDP** | Parameters, gradients, optimizer states | Reduces memory duplication across data-parallel workers. |

## 4. What is the benefit of data parallelism?

In **data parallelism**, every rank keeps a full copy of the model, but each rank processes a different mini-batch of data. After the backward pass, ranks synchronize gradients, usually with `all_reduce`, then each rank applies the same optimizer update.

Benefits:

- **Simple mental model.** The model code usually does not need to be split across devices.
- **Higher throughput.** If we use `K` workers, each worker handles part of the global batch.
- **Same result as large-batch training.** If gradients are averaged correctly, training is equivalent to computing the gradient on the combined global batch.
- **Good scaling when the model fits on one GPU.** Communication is mostly gradient synchronization, while forward/backward computation remains local.
- **Fault/debug simplicity compared with model parallelism.** Each worker has a complete model replica.

The main limitation is memory duplication: with standard DDP, every rank stores the full parameters, gradients, and optimizer states. For very large models, this becomes too expensive, so we use sharding approaches such as ZeRO or FSDP.

## 5. What is a model shard? How many copies of the model do we keep across K machines in a data-parallel communication group?

A **model shard** is one partition of the model state. Depending on the parallelism strategy, a shard may contain:

- a subset of parameters,
- a subset of gradients,
- a subset of optimizer state,
- or the layers/tensor slices assigned to one device.

If the model has `P` parameters and we shard it evenly across `K` ranks, each rank stores roughly `P / K` parameters, and the `K` shards together form one logical full model.

For **standard data parallelism / DDP**:

- each of the `K` ranks keeps a **complete model replica**;
- therefore there are **K full copies of the model** across the data-parallel group;
- gradients are synchronized so all replicas stay identical after each optimizer step.

For **sharded data parallelism** such as ZeRO-3 or FSDP:

- the `K` ranks in a sharding group collectively store approximately **one full copy** of the model parameters, split into `K` shards;
- each rank stores only about `1 / K` of the sharded state at rest;
- parameters may be temporarily gathered during forward/backward computation when a layer needs them.

So the answer depends on the strategy:

| Strategy | Model storage across K ranks |
|---|---|
| **Standard DDP** | `K` full copies |
| **Model/FSDP-style sharding** | About `1` full logical copy split across `K` shards |
