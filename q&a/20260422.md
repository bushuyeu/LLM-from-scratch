# GPU Performance Q&A — Roofline Model

## 1. What is Arithmetic Intensity?

**Arithmetic intensity** (AI), sometimes called *operational intensity*, measures how much compute a kernel does per byte of data it moves from memory. It's the ratio:

$$
\text{AI} = \frac{\text{FLOPs performed}}{\text{Bytes transferred from/to DRAM}}
$$

Units: **FLOPs/byte**.

### Why it matters

AI is a property of an *algorithm* (more precisely, of an algorithm's implementation on a given memory hierarchy) that tells you whether execution will be bottlenecked by the compute units or by the memory subsystem. It's the x-axis of the roofline plot.

### Examples (approximate, FP32)

| Kernel | FLOPs | Bytes moved | AI (FLOP/byte) |
|---|---|---|---|
| **Vector add** `c = a + b` (length N) | N | 12N (read 2 × 4B, write 1 × 4B) | **~0.08** |
| **SAXPY** `y = αx + y` | 2N | 12N | **~0.17** |
| **Dot product** | 2N | 8N | **~0.25** |
| **Dense GEMM** (large, blocked) | 2N³ | ~3N² (once blocks fit in cache) | **~N/1.5** → very high |
| **Attention softmax** | ~few × N² | ~8N² | **~0.5–2** |
| **Conv (3×3, stride 1)** | 18·H·W·Cin·Cout | depends on reuse | **moderate–high** |

### Important subtleties

- **Numerator**: count useful FLOPs (fused multiply-add = 2 FLOPs). GPU "TFLOPS" specs often assume FMA.
- **Denominator**: count bytes that actually cross the bandwidth boundary you care about — DRAM↔L2, HBM↔SM, NVLink between GPUs, etc. Each boundary gives a different AI.
- **Reuse** increases AI. Tiling/blocking GEMM keeps operands in shared memory / registers, dramatically raising effective AI and moving the kernel from memory-bound to compute-bound.
- **Precision matters**: FP16/BF16/FP8 halves or quarters bytes per element, raising AI for the same algorithm — one of the reasons low-precision training is faster on memory-bound kernels.

## 2. What is the Roofline Model?

The **roofline model** (Williams, Waterman, Patterson, 2009) is a visual performance model that bounds the achievable throughput of a kernel on a given machine as a function of its arithmetic intensity. The plot has:

- **x-axis**: arithmetic intensity (FLOP/byte), log scale
- **y-axis**: attainable performance (FLOP/s), log scale

### The roofline

$$
\text{Perf}_{\max}(\text{AI}) = \min\bigl(\text{Peak FLOP/s},\; \text{Peak Bandwidth} \times \text{AI}\bigr)
$$

Graphically this produces two "roofs":

- A sloped roof on the left — the **memory-bandwidth ceiling**, whose slope equals peak bandwidth (B/s).
- A flat roof on the right — the **compute ceiling**, the machine's peak FLOP/s.

They meet at the *ridge point* (see Q3). Any kernel's achieved performance is a single dot on this plane — the roofs tell you the best it could possibly do.

### What the regions mean

- **Left of the ridge (low AI)** → **memory-bound**. The kernel cannot feed the ALUs fast enough. Optimizations: increase reuse (tiling, fusion), compress data (lower precision, quantization), prefetch, use faster memory (shared memory, registers).
- **Right of the ridge (high AI)** → **compute-bound**. Memory isn't the bottleneck; you need more FLOPs per second. Optimizations: use tensor cores / vector units, FMA, better ILP, higher-throughput precision (FP16/FP8/INT8).

### Extensions

- **Multiple ceilings**: add rooflines for different instruction mixes (no-FMA, no-vectorization), different cache levels (L2, L1, shared memory → each has its own bandwidth and its own AI), or different power/thermal caps.
- **Hierarchical roofline**: one plot per memory level. A kernel that's DRAM-bound may still be far below its L2 or shared-memory ceiling, telling you what to optimize next.
- **Instruction roofline**: swap FLOPs for instructions or memory ops, useful for integer/irregular workloads.

### Example numbers (NVIDIA A100, SXM4 80GB)

- Peak FP16 tensor: **312 TFLOP/s**
- Peak FP32: **19.5 TFLOP/s**
- HBM2e bandwidth: **~2.0 TB/s**
- **FP16 ridge point**: 312e12 / 2.0e12 ≈ **156 FLOP/byte**
- **FP32 ridge point**: 19.5e12 / 2.0e12 ≈ **~10 FLOP/byte**

A LayerNorm or elementwise activation (~0.5 FLOP/byte) sits far to the left of both ridges — it will always be memory-bound. A large GEMM (~hundreds of FLOP/byte in FP16) sits well to the right — it can saturate the tensor cores.

## 3. What is the Critical Arithmetic Intensity?

The **critical** (or **ridge-point**) arithmetic intensity is the AI at which the memory-bandwidth roof and the compute roof intersect — the smallest AI at which a kernel can, in principle, saturate the machine's peak FLOP/s:

$$
\text{AI}_{\text{crit}} = \frac{\text{Peak FLOP/s}}{\text{Peak Bandwidth (B/s)}}
$$

Units: **FLOPs/byte** (same as AI).

### Interpretation

- If your kernel's **AI < AI_crit** → memory-bound. No matter how hard you optimize compute, bandwidth caps you at `BW × AI`.
- If your kernel's **AI > AI_crit** → compute-bound. You have enough reuse that memory isn't the limit; now the ALUs/tensor cores are.
- **At AI = AI_crit** → perfectly balanced; both resources are simultaneously saturated.

### The ridge has been creeping right

Modern accelerators add FLOPs much faster than bandwidth, so AI_crit has been growing — making more workloads memory-bound:

| Hardware | Peak (FP16 tensor) | HBM BW | AI_crit |
|---|---|---|---|
| V100 (2017) | 125 TFLOP/s | 0.9 TB/s | ~139 FLOP/byte |
| A100 (2020) | 312 TFLOP/s | 2.0 TB/s | ~156 FLOP/byte |
| H100 SXM (2022) | 989 TFLOP/s (FP16) / 1979 (FP8) | 3.35 TB/s | ~295 / ~590 |
| B200 (2024) | ~2250 TFLOP/s (FP8) | ~8 TB/s | ~280+ |

**Implication for LLMs**: inference (especially decode, with batch size 1) is overwhelmingly memory-bound on this hardware — token generation has AI close to 2 (one FLOP per weight byte read), two orders of magnitude below AI_crit. This is why KV-cache management, weight quantization (INT4/FP8), and batching matter so much — they either shrink bytes or raise effective AI.

### Practical use

1. Compute AI_crit for your target hardware + precision.
2. Estimate your kernel's AI analytically.
3. If AI ≪ AI_crit, don't bother tuning the math — focus on memory (fusion, tiling, precision).
4. If AI ≫ AI_crit and you're still below peak, the issue is instruction mix, occupancy, or tensor-core utilization.

## 4. What is a Kernel?

In GPU / parallel-computing terminology, a **kernel** is a function that runs on the accelerator, executed in parallel by many threads, each applying the same code to different data (SPMD — Single Program, Multiple Data). The host (CPU) *launches* the kernel; the device (GPU) runs it.

### Anatomy (CUDA model)

A CUDA kernel launch specifies a **grid** of **thread blocks**, each containing many **threads**:

```
grid  ─┬─ block (0,0) ─┬─ thread (0,0), (1,0), …
       │               └─ warp = 32 threads, scheduled together
       ├─ block (1,0) ─ …
       └─ …
```

- **Thread**: the smallest unit; has its own registers and program counter.
- **Warp**: 32 threads executing in lock-step (SIMT). Divergence within a warp serializes execution.
- **Thread block / CTA**: a group of threads (up to 1024) that run on the same SM, share **shared memory**, and can synchronize via `__syncthreads()`.
- **Grid**: the collection of blocks for one kernel launch.

### Minimal CUDA example

```cpp
__global__ void saxpy(int n, float a, const float* x, float* y) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) y[i] = a * x[i] + y[i];
}

// Host side:
saxpy<<<(n + 255) / 256, 256>>>(n, 2.0f, d_x, d_y);
```

- `__global__` marks the function as a kernel (host-callable, device-executed).
- `<<<grid, block>>>` is the launch configuration.
- Each thread computes its own index `i` from block/thread IDs.

### Kernel in broader contexts

The word "kernel" is overloaded — worth keeping the contexts separate:

| Context | Meaning |
|---|---|
| **GPU / CUDA / OpenCL** | Function executed in parallel on the device (this answer) |
| **ML frameworks (PyTorch, XLA, Triton)** | A fused, compiled compute unit — e.g., "FlashAttention kernel", "fused LayerNorm kernel" |
| **OS** | The privileged core of the operating system |
| **Signal processing / ML theory** | A function in a convolution or a kernel method (RBF kernel, etc.) |
| **Linear algebra / BLAS** | A basic op — `gemm`, `axpy`, etc. (as in "BLAS kernel") |

In this project's context (LLM-from-scratch, GPU training), "kernel" almost always means **a GPU function**, often a hand-written/fused one (Triton, CUDA, CUTLASS) whose performance you're analyzing against a roofline.

### Why kernels are the unit of performance analysis

Kernel launches are the atomic unit the GPU actually runs — scheduling, occupancy, memory access patterns, and roofline position are all *per-kernel* properties. Profilers (`nsight-compute`, `nsys`, `torch.profiler`) report metrics per kernel. Optimizations like **kernel fusion** (combining elementwise ops into one launch) reduce launch overhead *and* raise AI by avoiding intermediate round-trips to HBM.
