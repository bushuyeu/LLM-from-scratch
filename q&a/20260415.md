# CPU Architecture Q&A

## 1. What is cache?

**Cache** is a small, very fast memory that sits between the CPU cores and main memory (DRAM). Its purpose is to exploit **locality of reference** — both temporal (recently accessed data is likely to be accessed again) and spatial (nearby memory is likely to be accessed soon) — to hide the high latency of DRAM.

### Cache hierarchy (typical modern CPU)

| Level | Size | Latency | Scope |
|---|---|---|---|
| **L1** (split I/D) | 32–64 KB per core | ~4 cycles (~1 ns) | Per core |
| **L2** | 256 KB – 2 MB per core | ~12 cycles (~3 ns) | Per core (or shared cluster) |
| **L3** (LLC) | 8–128 MB | ~40 cycles (~10 ns) | Shared across all cores |
| **DRAM** | GBs | ~200–400 cycles (~100 ns) | System-wide |

### Key concepts

- **Cache line**: the unit of transfer, typically 64 bytes. Reading a single byte pulls the whole line.
- **Associativity**: set-associative caches map each address to N possible slots (e.g., 8-way).
- **Replacement policy**: usually (pseudo-)LRU — evict the least recently used line.
- **Coherence**: multi-core caches are kept consistent via protocols like **MESI** (Modified/Exclusive/Shared/Invalid).
- **Write policy**: write-through vs write-back (most modern L1/L2 are write-back).

A cache miss at L1 that reaches DRAM can cost ~100× more than an L1 hit — which is why cache-friendly data layout (arrays over linked lists, SoA over AoS, blocked matrix multiplication) matters so much for performance.

## 2. What are registers? How are they different from cache?

**Registers** are the tiny, fastest-possible storage locations **inside the CPU core itself**, directly referenced by machine instructions. They hold the operands that the ALU/FPU/SIMD units actually compute on.

### Typical register file (x86-64)

- 16 general-purpose 64-bit registers (`rax`, `rbx`, …, `r15`)
- 16/32 vector registers (`xmm0-15` / `ymm0-15` / `zmm0-31` for AVX-512)
- Special-purpose: `rip` (instruction pointer), `rflags`, segment registers, control registers

### Register vs cache — key differences

| Aspect | Register | Cache |
|---|---|---|
| **Location** | Inside the CPU core (part of the pipeline) | On-chip SRAM, outside the execution units |
| **Access latency** | 0 cycles (part of the instruction) | 4+ cycles (L1) to 40+ cycles (L3) |
| **Addressing** | Named directly in the ISA (`mov rax, rbx`) | Addressed by memory address; cache is transparent |
| **Size** | Bytes to a few KB total | KB to tens of MB |
| **Managed by** | The compiler (register allocation) | The hardware (automatic, transparent) |
| **Visibility** | Architecturally visible to the programmer | Transparent (visible only through performance) |
| **Per-core?** | Yes — one register file per hardware thread (physically more via register renaming) | L1/L2 per core, L3 shared |

**The crucial distinction**: registers are an **architectural abstraction** — part of the instruction set — while caches are a **microarchitectural optimization** — invisible to the ISA, there only to make memory accesses faster. A program can run correctly without caches (just slowly); it cannot run without registers.

Modern cores also have far more **physical** registers than **architectural** ones (e.g., 180+ physical vs 16 architectural on recent x86), thanks to **register renaming** for out-of-order execution.

## 3. What is a thread? What is a process?

### Process

A **process** is an instance of a running program. The OS gives each process:

- Its own **virtual address space** (code, heap, stack, mmap regions)
- Its own **file descriptor table**, signal handlers, environment variables
- A **PID** and resource accounting (CPU time, memory limits, etc.)
- Isolation: one process cannot directly read/write another's memory

Processes communicate through explicit IPC mechanisms: pipes, sockets, shared memory segments, signals, message queues.

### Thread

A **thread** is an independent execution context **within a process**. All threads in the same process share:

- The same virtual address space (heap, globals, code, mmap'd files)
- File descriptors, signal handlers, working directory

But each thread has its **own**:

- Stack
- Program counter / instruction pointer
- Register state
- Thread-local storage (TLS)
- Thread ID

### Process vs thread

| Aspect | Process | Thread |
|---|---|---|
| **Address space** | Isolated, separate | Shared with sibling threads |
| **Creation cost** | Expensive (`fork()` — new page tables, copy-on-write) | Cheap (`pthread_create` — just a new stack + TCB) |
| **Context switch cost** | Higher (TLB flush, page table swap on older HW) | Lower (same page tables) |
| **Communication** | IPC (pipes, sockets, shared memory) | Shared variables + synchronization (mutex, atomic, etc.) |
| **Fault isolation** | One process crashing doesn't kill others | A segfault in one thread typically kills the whole process |
| **Parallelism** | True parallelism across CPUs | True parallelism across CPUs (within the same process) |

### Note on Python

Python's **GIL** (Global Interpreter Lock) means CPython threads cannot execute Python bytecode in parallel — threads are good for I/O concurrency, but for CPU-bound work you need `multiprocessing` (separate processes) or release the GIL via C extensions (NumPy, PyTorch). Python 3.13 introduced an experimental no-GIL build that lifts this restriction.

## 4. What schedulers are used in multithreading / multiprocessing?

### OS-level (kernel) schedulers

These decide which thread runs on which CPU core at any given moment. The OS treats threads (not processes) as the schedulable unit on modern systems.

**Linux: Completely Fair Scheduler (CFS) → EEVDF (since 6.6)**
- CFS models "ideal fair multitasking" — each runnable task gets CPU proportional to its weight (derived from `nice` value).
- Uses a red-black tree keyed by **virtual runtime (vruntime)**; always picks the task with the lowest vruntime.
- **EEVDF** (Earliest Eligible Virtual Deadline First) replaced CFS in Linux 6.6 — similar fairness guarantees but with explicit latency targets.

**Other Linux scheduling classes**
- `SCHED_FIFO` / `SCHED_RR` — real-time, priority-based (preempts normal tasks).
- `SCHED_DEADLINE` — EDF-based for hard real-time.
- `SCHED_IDLE` — runs only when nothing else is runnable.

**Windows** uses a **multilevel feedback queue** with 32 priority levels and dynamic priority boosts (e.g., after I/O completion).

**macOS / XNU** uses Mach-based multi-level feedback with **Quality of Service (QoS) classes** — `USER_INTERACTIVE`, `USER_INITIATED`, `UTILITY`, `BACKGROUND`.

### Common scheduling policies (textbook)

| Policy | Description | Pros | Cons |
|---|---|---|---|
| **FCFS** | First-come, first-served | Simple | Convoy effect |
| **SJF / SRTF** | Shortest job (remaining) first | Optimal avg wait time | Starvation; requires knowing job length |
| **Round Robin** | Fixed time quantum, cycles through queue | Fair, responsive | Quantum tuning matters |
| **Priority** | Highest priority first | Supports urgency | Starvation (fix with aging) |
| **Multilevel Feedback Queue** | Multiple queues, tasks move between levels based on behavior | Adapts to I/O-bound vs CPU-bound | Complex to tune |
| **CFS / EEVDF** | Virtual-runtime fairness | Proportional fairness, low overhead | Not strictly real-time |

### User-space / runtime schedulers

Many languages and runtimes have their own schedulers **on top of** OS threads:

- **Go runtime** — **M:N scheduler** multiplexing millions of goroutines onto a pool of OS threads, using **work-stealing** across per-P (processor) run queues.
- **Tokio (Rust)** — multi-threaded work-stealing scheduler for async tasks.
- **Java ForkJoinPool** — work-stealing for fork-join parallelism; used by parallel streams and virtual threads (Project Loom).
- **.NET ThreadPool** — hill-climbing heuristic to decide how many worker threads to run.
- **OpenMP / TBB** — task/loop scheduling for parallel regions (static, dynamic, guided chunking).
- **Python `asyncio`** — single-threaded cooperative event loop; tasks yield at `await` points.

### Key scheduling concepts

- **Preemptive vs cooperative**: can the scheduler forcibly suspend a task, or does the task have to yield? (Linux CFS: preemptive; Python `asyncio`: cooperative.)
- **Work stealing**: idle worker threads steal tasks from busy workers' queues — the basis of Go, ForkJoinPool, Tokio, TBB.
- **CPU affinity**: pinning threads to specific cores to preserve cache state; tunable via `taskset`, `sched_setaffinity`, `pthread_setaffinity_np`.
- **NUMA awareness**: on multi-socket systems, schedulers try to keep a thread on the socket whose memory it's touching.
- **Load balancing**: periodic rebalancing across CPUs/run queues to avoid idle cores.
